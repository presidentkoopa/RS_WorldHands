// The reach OVAL, per hand. Hand-local semi-axes: x ACROSS THE PALM, y ALONG
// THE FINGERS, z through the back of the hand. 34 units is a metre; a fist is
// about 2 units.
//
// X IS SIDEWAYS AND Y IS FORWARD, and the letters were the other way round in
// this comment until 2026-08-26. They are not ours alone to name: MODELDEF hands
// these six names to the engine as `PlacementCVars rs_grab_m`, which sums _ofs_x
// into the same matrix component as vr_hand_ofs_x -- captioned "Left / Right" --
// and scales the mesh's sideways axis by _scale_x. The script that TESTS the
// volume read x as forward, so the drawn oval and the tested ellipsoid were
// mirror images of each other's shape, and the offset slider captioned
// "Forward / back" pushed one along the fingers and the other sideways.
//
// The defaults below swapped with the fix: 3.2 is still the long axis and it is
// still along the fingers, it is simply on the letter that actually draws there.
// An ini with tuned numbers in it keeps them and needs one re-dial.
//
// An oval and not a sphere: a hand reaches further along the fingers than it
// does through the back of the wrist, and a sphere wide enough to touch the
// fingertips also grabs things behind you.
//
// _scale is the master multiplier over all three axes, and it has a slider now.
// The three per-axis numbers say the SHAPE; this one says the SIZE. With only
// the first three, making the whole volume smaller meant moving three sliders in
// step and hoping they stayed in proportion.
//
// Its range reaches down to 0.005 because the drawn volume rides the hand
// through the same transform the viewmodel uses, and that space is NOT the 34-
// units-to-a-metre of the world path. A unit-radius mesh arrives already metres
// across. Trim SIZE first, then dial the three axes for shape.

// WHICH SPACE THE SIX NUMBERS ABOVE ARE IN. 0 = map units, which is how the
// grab test has always read them. 1 = the drawn mesh's own space, where one unit
// is one METRE -- because the oval rides GetWeaponTransform, and that matrix
// carries a scale of vr_vunits_per_meter.
//
// THIS IS A HEADSET QUESTION AND IT CANNOT BE ANSWERED FROM THE SOURCE. Both
// readings are argued for in this tree by people who were right about other
// things: MODELDEF.txt asserts map units outright, the comment above and the
// 0.005 slider floor only make sense in mesh space, and the two have been
// disagreeing in writing for as long as both files have existed.
//
// So the test implements both and this picks. It defaults to 0 -- the behaviour
// that has always been in force -- so nothing moves for anyone who does not go
// looking. Flip it to 1, look at the oval, and keep whichever one puts the drawn
// volume where things actually get grabbed.
//
// Under 1 the OFFSETS are read as multiples of the semi-axis rather than as map
// units, because that is what the renderer does with them: the placement scale
// is applied outside the placement offset, so the drawn oval moves by
// ofs * scale * master and not by ofs.
// 1, NOT 0. The shipped master (0.025) and axes (1/4/3) were dialled in a
// headset against the DRAWN oval, which the renderer scales in mesh space;
// read as map units (space 0) they floor to a ~0.05-unit ellipsoid, so a
// near grab only ever succeeded with the palm physically inside the target's
// collision cylinder while the gauge showed a reach forty times larger.
user int rs_grab_scale_space = 1;

// THE TWELVE NUMBERS BELOW ARE DIALLED IN A HEADSET, 2026-08-29, and replaced
// the theoretical ones this file shipped with. They came out of the owner's own
// config after tuning against the drawn oval, so they are what a hand-sized
// grab volume actually measures rather than what it ought to.
//
// The master scale is the striking one: 0.025 against the old 1.0. That is not
// a small correction, it is a fortyfold one, and it is the strongest evidence
// yet on the rs_grab_scale_space question above -- numbers that need a 0.025
// master to look right are not being read as map units in practice, whatever
// space 0 nominally selects. Left at 0 because that is the reading in force and
// the volume now measures correctly under it; noted because if anyone ever
// flips that cvar, these twelve all have to be re-dialled with it.
//
// Per-axis shape changed too, and meaningfully: y (along the fingers) went 3.2
// -> 4.0 and z (up through the hand) 1.6 -> 3.0, while x (across the palm)
// dropped 2.2 -> 1.0. So the volume is now much narrower across the palm and

user float rs_grab_m_pitch = 0.0;
user float rs_grab_m_roll = 0.0;

// REACH AND SPREAD ARE SEPARATE NUMBERS on purpose. How FAR you can pull from
// and how PRECISELY you must point are different complaints with different
// fixes, and one combined "cone size" slider forces one of them to be wrong in
// order to get the other right. 34 units is a metre, so 512 is about 15m.
user float rs_dgrab_reach = 512.0;
// HALF-angle, degrees. 12 is a cone about the width of a doorway at 10 metres.
// WIDENED 12 -> 25, 2026-08-30. Twelve degrees is forgiving at arm's length
// and a needle at range, and a log run ended with four squeezes and four
// "cone found nothing" in a row. Pointing a tracked controller at a clip on a
// floor ten metres away does not have twelve degrees of precision in it.
user float rs_dgrab_spread = 25.0;

// HOW FAST IT TRAVELS, metres per second -- not how long it takes. Flight time
// is derived from the distance, so a thing across the room and a thing at your
// feet arrive at the same speed. A fixed tic count made the far pull a blur and
// the near one a drift, off one slider.
user float rs_dgrab_speed = 15.0;

// Floor and ceiling on that, in tics. 35 to a second.
user float rs_dgrab_time_min = 6.0;
user float rs_dgrab_time_max = 70.0;

// ACCELERATION. 1 is constant speed; above 1 starts slow and speeds up, which

user float rs_dgrab_accel = 1.6;

// Arc height as a FRACTION OF THE LAUNCH DISTANCE, so the arc keeps its shape at
// every range instead of a long pull reading flat and a short one as a lob.
//
// A NEW NAME, not the old rs_dgrab_lift, and that is deliberate. The old one
// meant map units and is sitting in inis at 24; reusing it with a fractional
// meaning would give a 512-unit pull an arc twelve thousand units high. A
// CVARINFO default cannot override a saved value -- a fresh name is the only way
// a changed meaning ever actually takes.
user float rs_dgrab_arc = 0.15;

// TUMBLE. How many turns end over end the object makes on its way to you,
// across the WHOLE flight rather than per second -- so a pull from across the
// room and one from arm's length both arrive having turned the same amount,
// exactly as the arc height is a fraction of the distance rather than a fixed
// number of units. Negative turns it the other way.
//
// WHOLE NUMBERS ARE THE POINT. The flight restores the object's original roll
// on arrival, so that a caught barrel is not left cocked at whatever angle it
// happened to reach you at -- and landing on a whole turn makes that restore
// the same angle the object is already showing, so it is invisible. 1.5 is
// perfectly legal and will visibly snap the half turn as it lands.
//
// 0 IS OFF, and off means untouched: at zero the flight never sets the render
// flags at all, because +ROLLSPRITE is not inert at roll zero -- it changes how
// the sprite is scaled, and +ROLLCENTER drops the sprite's own offsets.
//
// DEFAULT 0.5 ON TASTE, 2026-08-29 -- "beautiful" in the headset, and two full
// turns is a lot of motion on something you are trying to track and catch. It
// deliberately breaks the whole-number rule above: half a turn means the roll
// restore on arrival snaps 180 degrees. That is invisible on a barrel, which is
// symmetric end to end, and it is what most pulled objects are. Set a whole
// number if a snap ever shows on something that is not.
user float rs_dgrab_tumble = 0.5;

// Refuse to pull things you cannot see. Off lets you grab through walls.
user bool rs_dgrab_sight = true;

// ---- FLICK --------------------------------------------------------------
//
// Open an empty hand while the cone has something locked and it comes to you,
// no button. Only ever fires with a lock, and only when the release carries the
// gesture below -- so simply letting go still just lets go.
user bool rs_dgrab_flick = true;

// WHICH GESTURE. 0 = pull the hand back, 1 = tip the wrist up.
//
// 1 by default as of 2026-08-28, for comfort rather than for anything
// technical. Dragging the hand back toward the body is a SHOULDER movement,
// and seated with an elbow on an armrest that is precisely the motion you
// cannot repeat -- which is how this mod is actually played. Tipping the wrist
// is the same intent through the joint that is still free.
//
// A MODE AND NOT A PAIR. Accepting either gesture would put the shoulder-pull
// back as an accidental trigger for exactly the player the wrist gesture is
// for: draw your hand back to rest it, and the pull fires.
user int rs_dgrab_flick_mode = 1;

// Metres per second, for mode 0. Measured as the PEAK of the last ~180ms
// rather than the speed at any single moment. Your arm is already slowing down
// by the end of a gesture, so the last sample always reads slower than the
// flick felt.
user float rs_flick_speed = 2.5;

// DEGREES PER TIC, for mode 1. A RATE, not a total -- which is the whole point:
// a slow deliberate lift of the forearm never crosses it however far it
// travels, while a sharp tip of the wrist crosses it at once. That is what
// separates the gesture from ordinary aiming.
//
// 5.0 is ~175 degrees a second, a brisk but unhurried flick. Raise it if the
// pull ever fires while you are simply aiming upward; do not shorten the
// sample window instead, since the peak-over-window is what stops the gesture
// reading as weak just because your wrist is already settling by the time your
// fingers open.
user float rs_flick_pitch = 5.0;

// The line from your palm to what you have locked. Answers "what will I get",
// which is the question you have while pointing -- a drawn cone would answer
// "where can I aim", which is the one you do not.
user bool  rs_dgrab_beam = true;

// Flash whatever you are pointing at, and whatever is in your hand.
//
//   considered / lasered over    neutral <-> orange
//   in your hand                 orange  <-> green
//   in flight toward you         nothing -- the arc is the feedback by then
//
// A translation remap rather than a model swap: a voxel is bound to a SPRITE
// NAME and resolved before any per-instance override is read, so hiding one
// gets you an invisible object rather than a sprite. Colours are in TRNSLATE.
user bool rs_grab_lightup = true;

// Tics for a full cycle. 35 to a second, so 24 is a slow pulse -- fast enough
// to read as alive, slow enough that a room full of pickups is not a strobe.
user float rs_grab_flash = 24.0;


// ---- THROWING -----------------------------------------------------------
//
// Letting go and throwing are the same act; the difference is how fast the hand
// was moving. Speed comes from the PEAK of the last ~180ms, not the instant of
// release -- your arm is already slowing by then, and a throw built on that
// number comes out limp however hard it felt.
user bool rs_throw = true;

// Metres per second below which a release is a DROP. Under it the object leaves
// at the hand's current speed instead of inheriting a peak from a fifth of a
// second ago -- otherwise setting something down right after catching it makes
// it leap out of your hand.
user float rs_throw_min = 1.2;

// Multiplier on the throw. 1.0 is your actual arm speed.
user float rs_throw_scale = 1.0;

// Same, but only for the OFF hand, on top of the multiplier above. Most
// people's off arm genuinely throws with less wrist snap and follow-through
// than their main arm -- tracking has nothing to do with it. 1.0 leaves the
// off hand alone; raise it if your off-hand throws feel consistently short.
user float rs_throw_scale_off = 1.0;

// ---- HOW A THROW IS READ OFF YOUR ARM -------------------------------------
//
// AIM FROM THE RELEASE, SPEED FROM THE PEAK.
//
// Your hand travels an ARC. Its fastest instant is several tics before you let
// go and is pointing somewhere else along that curve -- so a throw that takes
// both speed and heading from the peak sends the object where your hand was a
// fifth of a second ago rather than where you were aiming when you opened your
// fingers. That is why throwing felt wrong rather than merely weak.
//
// How many of the newest samples are averaged for the HEADING. One tic of a
// tracked hand is noisy and a throw is too committed a gesture to hand its
// direction to 28 milliseconds of jitter; more than about four and you are
// averaging in the part of the arc before you committed.
user int rs_throw_aim = 3;

// How recently the fast bit must have happened, in tics, for it to count as
// THIS throw. The window holds about a fifth of a second, so without this a
// flick made before you even picked the object up is still the newest peak and
// becomes its throw -- which reads as the game launching things at random.
user int rs_throw_grace = 4;

// ---- THE ARC --------------------------------------------------------------
//
// Upward velocity added in proportion to how hard you threw. People lob things
// without noticing; in a headset almost nobody does, because the motion your
// body makes is a straight push at what you are looking at. Taken literally,
// every throw is a flat line drive that lands short -- which reads as weak
// rather than as level.
//
// Proportional to FLAT speed, so a gentle toss stays gentle, a hard throw arcs,
// and throwing straight up does not add more up. 0 for a dead-flat throw.
user float rs_throw_lift = 0.35;

// ---- SPIN -----------------------------------------------------------------
//
// The rotation your wrist put on it. Nothing thrown in this project span until
// this existed: the swing tracker sampled position and pitch only, so there was
// no angular velocity to give an object even if something had asked for one.
//
// Separate from throw strength because they are separate intents -- a hard
// straight throw and a lazy spinning one are both things a player means, and
// one multiplier cannot express both.
user bool  rs_throw_spin = true;
user float rs_throw_spin_scale = 1.0;

// ---- USING WHAT YOU ARE HOLDING -----------------------------------------
//
// Bring it to your face. This is the counterpart to switching walk-over off:
// once the room stops emptying itself as you cross it, a pickup has to be used
// somewhere, and that somewhere has to be a place you can only reach on purpose.
//
// Not your body -- a held object is permanently inside your own collision
// cylinder, so consuming on body contact is the walk-over behaviour again under
// a different name.
user bool rs_use_at_face = true;

// How close to your head, in map units. 34 is a metre, so 12 is about a hand's
// length from your face.
user float rs_use_face_reach = 12.0;

// Ammo goes to the chest pouch instead of resolving when you catch it.
//
// LIVE AS OF 2026-08-28, and on. This shipped inert for a long time with a note
// saying the pouch it would route to "died with RS_UnifiedVR" -- the switch was
// left in place so the decision was recorded and the menu row was ready for
// when a pouch came back. It came back: RS_Holsters' ammo pouch is the same
// anchor RR_Reload draws magazines out of, so ammunition now goes back in the
// way it comes out.
//
// WHY THIS IS THE BETTER DEFAULT. A box you DON'T catch lands at your feet and
// is collected by standing there anyway. So absorbing one on the catch produces
// the identical outcome as missing it, which makes catching worthless -- you
// did something skilful and the game gave you what it would have given you for
// nothing. Holding it until you put it away is what makes the catch an act
// rather than an event.
//
// Off restores the old behaviour: caught ammunition resolves instantly and
// never reaches your hand.
user bool rs_use_ammo_pouch = true;

// A tick when a held item crosses into face range.
//
// HAPTICS HAVE NEVER BEEN PROVEN TO WORK IN THIS TREE. This is wired and
// instrumented rather than assumed: turn on the engine's vr_haptic_debug and
// read [HAPTIC]. Nothing printed means the call never left. "runtime accepted"
// printed and nothing felt means the problem is past this code. Either is an
// answer; neither is a guess.
user bool  rs_use_face_haptic = true;
user float rs_use_face_haptic_amp = 0.35;

// A wire sphere at your head, sized to the face reach, so what you see is what
// triggers -- the same discipline the grab oval uses. OFF: it is for dialling
// the number in, not for playing with.
user bool rs_use_face_viz = false;

// ---- TWO-HAND STABILIZE ------------------------------------------------
//
// The off hand braces the weapon in the main hand -- see rs_stabilize.zs for
// the whole story. Short form: every weapon model carries a support point,
// an oval drawn on the gun; the off hand's reach oval meeting it plus a
// squeeze is the brace, published to the engine as a forend / foregrip /
// support claim. The engine's own "Two Handed Weapons" option (Options > VR
// Controls) is what then makes the aim follow the hands; leave that off and a
// brace is a pose and a hold flag only.
user bool  rs_stab = false;   // owner's tuned value, baked in 2026-09-15 (was true)
user bool  rs_stab_viz = false;   // owner's tuned value, baked in 2026-09-15 (was true)
// Hold to keep (off, the default): braced while the off grip stays squeezed
// inside the oval, exactly as the original grip-to-stabilize worked. Tap to
// latch (on): one squeeze attaches, the grip is free again until the next.
user bool  rs_stab_latch = false;
// WHERE A SWAP IS ALSO POSSIBLE -- the two hand ovals overlapping, which on
// a pistol is the same place as the support oval -- a brace wants the MAIN
// grip held at the moment of the tap: you cannot take a gun from a hand that
// is gripping it, and you do not brace one that is not. Anywhere else (a
// rifle's forend is a forearm from the other palm) the main grip is not
// consulted. Off makes the brace win whenever the hand is in the oval.
user bool  rs_stab_need_main_grip = true;
user bool  rs_stab_haptic = true;
user bool  rs_stab_debug = false;
// How far inside the support oval the off palm must be, in oval radii: 1.0
// is the drawn surface, more counts a hand that far outside it as in. A
// little over 1 by default, because the palm is a controller estimate.
user float rs_stab_depth = 1.25;
// How far a braced hand may drift before it lets go, same units. Wider than
// the entry depth on purpose -- a hand on a forend does not sit on one exact
// spot.
user float rs_stab_break = 2.5;
// The flat distance the test falls back to when either oval is too small to
// decide it, map units. See RS_Reach.OvalsOverlap for why that can happen.
user float rs_stab_min = 6.0;

// THE DISTANCE GRAB STANDS DOWN WHILE YOUR HANDS ARE TOGETHER.
//
// Bringing the palms into one another always means something local -- passing a
// weapon across, racking a slide, taking a second hand to a grip. None of it
// means "lock that barrel across the room", but the cone could not tell, so a
// two-handed hold arrived with something distant locked and flashing, and
// opening the hand flicked it at you.
//
// The near grab is untouched: closing on a thing your palm is inside is
// unambiguous however your hands are arranged.
user bool rs_dgrab_not_when_met = true;

// A HELD OBJECT IS DRAWN LOCKED TO THE CONTROLLER.
//
// The playsim still moves it with TryMove -- so it collides, stops at walls and
// the hold still breaks when it snags -- but what you SEE is resolved at draw
// rate in the hand's own frame. Placed from script alone it lagged the hand by
// two or three frames and swam around it, with no orientation of its own.
//
// Off puts it back to the script position: steadier on a machine that cannot
// keep the frame rate up, and honest about exactly where the object is.
// OFF BY DEFAULT until it is proven on more than a magazine.
//
// Drawing a held object in the controller's frame fixes the orbit, but it puts
// EVERY held thing -- barrels, medikits, corpses -- onto the follow-hand path,
// where the model-unit conversion applies and a world-scaled MODELDEF is a
// hundred times too small. A magazine has its own placement prefix and comes
// out right; a barrel does not, and the failure looks like the object
// vanishing.
//
// So it stays available and stays off. The magazine drawn from the pouch does
// not go through this at all -- RS_TestPistol sets FollowHandMode on it
// directly, with its own prefix and its own scale.
user bool rs_hold_followhand = true;   // owner's tuned value, baked in 2026-09-15 (was false)

// A WEAPON SWAP NEEDS THE PALM TURNED UP.
//
// Overlapping ovals alone was the whole test, so any two hands brought together
// traded guns -- including the postures that mean something else: a hand coming
// UNDER a pistol to brace it, and a hand coming OVER the top to work the slide.
// Both put the palms together by definition, and both swapped instead.
//
// Turning a palm over and closing it is deliberate, and nothing else in the

user bool rs_swap_needs_palm = true;
